# Key management

NetOidc signs ID tokens, JWT access tokens, JARM responses, signed UserInfo responses and
logout tokens; it decrypts request objects encrypted to it; and, with OpenID Federation, it
signs its entity statements. This guide covers how to configure those keys, rotate them and
keep them outside the process.

## Key kinds

| Use (`ProviderKeyUse`) | Registered with | Algorithms | Published in |
|------------------------|-----------------|------------|--------------|
| `Signing` | `AddSigningKey`, `AddSigningCertificate` | RS256/384/512, PS256/384/512, ES256/384/512 | `jwks_uri` |
| `Encryption` | `AddEncryptionKey` | RSA-OAEP | `jwks_uri` (`use: enc`) |
| `Federation` | `AddFederationKey` | as for signing | the entity configuration only, never `jwks_uri` |

RS*/PS* and RSA-OAEP need RSA keys (2048 bits or more); ES256, ES384 and ES512 need P-256,
P-384 and P-521 keys. RSA-OAEP-256 and ECDH-ES are not supported by Microsoft.IdentityModel
and are refused at startup; RSA1_5 is refused on purpose (RFC 8725 §3.2).

## Configuring keys

```csharp
builder.Services.AddNetOidc(options =>
    {
        options.DefaultSigningAlgorithm = "PS256";   // used when a client asks for nothing specific
    })
    .AddSigningCertificate(LoadCertificate("signing.pfx"), "PS256")   // x5c is published
    .AddSigningKey(new ECDsaSecurityKey(ecKey), "ES256")
    .AddEncryptionKey(new RsaSecurityKey(encryptionRsa))
    .AddFederationKey(new RsaSecurityKey(federationRsa), "RS256");     // only with FederationEnabled
```

- A client can ask for a specific algorithm (`id_token_signed_response_alg`,
  `userinfo_signed_response_alg`, `authorization_signed_response_alg`). Register one active key
  per algorithm you want to offer; discovery advertises exactly the algorithms of active keys.
- OpenID Connect certification (Basic, Implicit, Hybrid) requires an RS256 key. FAPI requires
  PS256 or ES256.
- `kid` defaults to the key's own id, then its RFC 7638 thumbprint. Set `keyId:` to fix it.

### Startup checks

`KeyRingStartupCheck` stops the host when:

- the environment is **Production** and any key was generated by the provider (no keys configured);
- a key's algorithm is unsupported, or does not match its key type or curve;
- two keys share a `kid`;
- no signing key is active.

Outside Production, the provider generates whatever is missing (an RS256 signing key, an
RSA-OAEP encryption key and, with `FederationEnabled`, a federation key) so that samples run
without setup. Generated keys change on every restart and differ per instance. In Production an
encryption key is never generated: without a configured one, encrypted request objects are simply
not offered.

## Rotation

Every key can carry `notBefore` and `notAfter`:

| State | Signs / decrypts | Published and verifies |
|-------|------------------|------------------------|
| before `notBefore` | no | yes |
| between `notBefore` and `notAfter` | yes | yes |
| after `notAfter` | no | no |

When several active keys share an algorithm, the one with the latest `notBefore` signs. A
rotation with no failed validations looks like this:

1. **Publish the successor early.** Add the new key with `notBefore` = now + the longest time a
   relying party caches your JWKS (24 hours is a safe default). It appears in `jwks_uri`
   immediately but is not used yet.
2. **Switch.** At `notBefore` the new key starts signing. Tokens signed by the old key still
   verify, because the old key is still published.
3. **Retire the old key.** Give it `notAfter` = switch time + the longest lifetime of anything it
   signed (refresh-token-bound ID tokens are not re-verified, so this is usually the access-token
   or ID-token lifetime, plus the relying parties' JWKS cache time). After `notAfter` it drops out
   of the JWKS.

For encryption keys, publish the successor early in the same way: clients encrypt to a key they
found in the JWKS, and the provider decrypts with every published encryption key.

```csharp
.AddSigningCertificate(current, "PS256", notAfter: switchAt.AddDays(2))
.AddSigningCertificate(next, "PS256", notBefore: switchAt)
```

Keys are read on every use, so a key store (below) can rotate without restarting the host.

## Keys in a vault, HSM or KMS

Implement `IKeyStore` to supply keys from anywhere:

```csharp
public sealed class VaultKeyStore(IMemoryCache cache, IVaultClient vault) : IKeyStore
{
    // Called on every signing operation: cache, and refresh in the background.
    public IReadOnlyList<ProviderKey> GetKeys() => cache.GetOrCreate("netoidc-keys", entry =>
    {
        entry.AbsoluteExpirationRelativeToNow = TimeSpan.FromMinutes(5);
        return vault.LoadProviderKeys();
    })!;
}

builder.Services.AddNetOidc(o => { /* ... */ }).UseKeyStore<VaultKeyStore>();
```

When the private key never leaves the device, supply:

- `Key`: a `SecurityKey` whose `CryptoProviderFactory` returns a `SignatureProvider` (or a key
  wrap provider, for decryption) that calls the HSM/KMS;
- `PublicJwk`: the public key to publish, because it cannot be derived from the device key.

```csharp
.AddKey(new ProviderKey
{
    Key = new KmsSecurityKey(kmsClient, keyArn) { CryptoProviderFactory = new KmsCryptoProviderFactory(kmsClient) },
    PublicJwk = kmsPublicJwk,
    Algorithm = "PS256",
    ExplicitKeyId = "kms-2026-09",
})
```

`GetKeys` is synchronous and called on hot paths: never make a network call from it without a
cache.

## Operations

- `builder.Services.AddHealthChecks().AddNetOidcKeys()` reports **Unhealthy** without an active
  signing key, and **Degraded** for generated keys or when every active signing key expires within
  a week (`warnBefore`) with no successor published.
- Keep private keys out of source control and configuration files; load them from a certificate
  store, Key Vault, KMS or a mounted secret.
- Every instance must use the same keys. Generated keys, or keys loaded per instance, produce
  tokens that other instances cannot verify.
- DPoP server nonces (`DPoPRequireNonce`) are HMACs: set the same `DPoPNonceSecret` on every
  instance and rotate it like any other secret.
- Pairwise subjects are derived from `PairwiseSalt`. Changing the salt changes every pairwise
  `sub`, which relying parties see as new users; treat it as permanent.
